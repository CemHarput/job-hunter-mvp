## Problem (observed in the first real scan, 2026-11-06)

Most are NOT applicable from Ankara, Türkiye, because `evaluate()` only rejects explicit phrases in the text ("US only", "must be based in…"); the structured `location` field is not used to eliminate anything. ## Wanted behavior (planner should refine and make concrete decisions)
1. Classify each job's location (plus remote signals from title/description where location is empty/ambiguous) into outcomes using the existing statuses where possible (`ineligible`, `global_unconfirmed`, `unknown`, `candidate_tr`), never VERIFIED:
   - Restricted → `ineligible` with evidence naming the location (e.g. "Location restricted: United States (Remote)"): every listed alternative is a specific non-Türkiye country/city/region, or on-site/hybrid/in-office with no remote option (bare "Hybrid", "In-Office", "Berlin", "San Francisco, CA | New York City, NY", "Remote, Canada; Remote, United States", "Americas", "NAMER and LatAm").
   - Open-ish → keep as `global_unconfirmed` (or a clearer regional label) when ANY alternative is open to a region that could include Türkiye: Worldwide/Global/Anywhere/EMEA/Europe(?)/"Home based - EMEA". Decide how to treat Europe/EMEA: geographically includes/near Türkiye but employer hiring/legal entity unknown → must stay unconfirmed, flagged "bölgesel (EMEA/Europe), Türkiye doğrulanmadı". Never mark VERIFIED.
   - Türkiye explicitly in location ("Turkey", "Türkiye", "Istanbul", "Ankara") together with remote → keep existing `candidate_tr`; Türkiye on-site/hybrid in a city is NOT remote-eligible from Ankara unless Ankara/remote.
   - Bare "Remote" or empty location → `unknown` (not rejected), let description/eligibility-checker decide.
   - Multi-value locations (`|`, `;`, `/`, " or "): eligible if ANY alternative is open; restricted only if ALL alternatives are restricted.
2. Maintain a data-driven, editable table (YAML in config/, e.g. `config/locations.yaml`, or inside profile.yaml): country/region/US-state/city tokens -> kind (restricted-country, open-region, turkiye), so the user can adjust without code changes; include country names + common codes/aliases, major cities seen in data, US state abbreviations after a comma ("San Francisco, CA"), UK/EU variants. Unknown tokens (cannot classify) must NOT cause rejection: classify `unknown` and surface unclassified location strings (e.g. a `python -m jobhunter locations` command or a report footer listing unclassified strings with counts) so the table can be extended.
3. Report volume: restricted jobs must stay visible but not flood the report (651 listed today). Decide a compact presentation (e.g. "Elenen ilanlar" grouped by reason/location with counts and a compact one-line-per-job list or a separate archive file, full detail via a `list --rejected` option) while keeping the matched evidence for each rejection auditable in the DB/archive. Hard CLAUDE.md rule: no job is silently hidden.
4. Existing DB: after the rules change, `scan` re-evaluates every job (upsert overwrites the heuristic fields). Jobs already marked reported stay reported; reviewed_status always wins and `excluded` stays final. Provide a way to re-evaluate stored jobs without network (e.g. `python -m jobhunter reevaluate`) that updates eligibility_status/evidence/score only, never reviewed_*/reported_* fields; ensure the previously listed (reported) jobs now classified ineligible can be seen via `list`/report archive.
5. Interaction with the previous feature's behavior: keep the conservative text-based NEGATIVE patterns, the contract-length rule, low-priority scoring, review/reported markers, baseline and age filter. The location result must be combined with text results with clear precedence (excluded > irrelevant > text-negative/ineligible > location-restricted > contract > remote/Türkiye logic).
6. Scoring: open-region/worldwide remote jobs rank above regional-unconfirmed, which rank above unknown; keep scores 0..100.
7. Tests with real-looking fixtures taken from the strings above (each listed string as a parametrized case with expected outcome), multi-value cases, unknown-token handling, reevaluate not touching reviewed/reported fields, report compaction, and no regression of the existing 70 tests (`python -m pytest -q`).
